# dsh-memory-switch

记忆上下文注入的**会话级开关**。

面板里 `@restregular/dsh-memory` 的那几个开关是**全局**的 —— 改一次所有会话一起变。
本插件补上缺的那一格：**每个会话自己决定**要不要让记忆往上下文里注东西。

## 关掉之后发生什么

只停「往上下文里注入」，**不停记忆本身**：

- `memory_save` / `memory_search` / `memory_get` / `memory_list` 照常可用 —— 模型想知道什么可以自己查；
- 记忆照旧落盘，别的会话、面板、以后的会话都不受影响。

## 已知代价（必须说清楚）

本插件是**在注入发生之后把记忆摘掉**，不是让 `dsh-memory` 一开始就不注入。这是本方案最重要的短板：

- 每轮召回仍会在后台查一次（白花一点 CPU 与向量检索时间）；
- **更严重：关着开关也会消耗上游的「已送达」状态。** 上游在生成时就写 `markDigestDone()`
  (`lib/inject/apply.js:1112`)、`markContent` / `markHint` (`1129-1131`)、
  以及把规则正文当已进系统提示 (`1181-1184`)。本插件用 `await next()` 拿到结果时，
  这些副作用**已经发生了**，删消息撤不回来。

后果：关着默认聊过几轮再打开，那条新会话的一次性摘要和部分召回**不会补发** ——
上游以为送过了，按版本去重直接跳过 (`state.js:224-228`)。重启也救不了，`digestDone` 是持久化的 (`apply.js:670`)。

所以准确定位是**输出过滤器**，不是「让记忆完全不工作」。
**不要承诺「打开就立刻有摘要和召回」。**

要根治只有一条路：让 `dsh-memory` 在**生成前**查一次会话开关，关闭时既不生成、也不消费那些 done/去重状态
（需要改上游代码）。

这个代价是刻意接受的：相比「动手改上游包、它一升级就失效」，「少一次摘要」的用户可见损失小得多，而且随时可拆。

## 为什么不能只改 dsh-memory 的配置

它的注入半边没有会话维度的开关，面板上的选项写的是全局状态。
