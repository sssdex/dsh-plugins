# dsh-token-tree

**把父代理和它所有子孙代理的 token 消耗加在一起，常驻在右侧栏。**

## 这个插件解决什么

DSH 内核的 token 计量**全部按单个 Session 算**：`ctx.tokenMeter`、`contextPressure`、`tokenUsage` 三个投影都吃一个 `session` 参数。而每个 subagent 是一个独立 Session —— 父会话日志里只有一条 `subagent/catalog` 事件记住 `childId`，从没有地方把子会话的用量汇总回父会话。

结果就是：**界面永远只显示当前这个 agent 的用量，你永远看不到「这一整轮多智能体总共烧了多少」。**

`dsh-context` 的「编队 / Fleet」页能看到每个子 agent 的卡片，但它给的是**费用估算**，两行的提示原文是：

- `仅当前 Agent 会话自身的累计费用估算（不含子 Agent）`
- `全部层级的子 Agent 会话各自累计费用（同口径估算）的合计，不含当前 Agent 自身`

它没有 token 口径的合计键（`subTokensTip` / `fleetTokens` 这些键根本不存在），所以想看 token 总数还是没办法。

本插件补的就是这一层。

## 怎么用

装好后（见下）有两种打开方式：

1. **会话标题栏右上角**的 `Σ` 图标按钮（28×28，和旁边的原生图标按钮同尺寸，悬停看全名），点一下在右侧栏打开。
2. 右侧栏的 **+** → 引导页里的「父+子 Token」卡片。

面板内容：

| 区块 | 说明 |
|---|---|
| **父 + 全部子孙** | 一个大数字 + 精确值；下面四格：**缓存命中率**、代理数、步数、请求数 |
| **根自身 / 子代理** | 两行占比条，一眼看出这轮是谁在烧 token |
| **Token 组成** | 一条堆叠条 + 图例：未缓存输入 / 缓存命中 / 缓存写 / 输出，各自数值与占比 |
| **代理树** | 每个代理一行：名称、billed（或 fresh）、代理数 / 步 / 请求 / **命中率**；有子代理的行可折叠 |
| **计费 / 新增 切换** | `计费`（billed）= 未缓存输入 + 缓存读 + 缓存写 + 输出；`新增`（fresh）= 未缓存输入 + 输出 |
| **⧉ 复制** | 把树按文本形式复制走（含命中率） |
| **自动刷新** | 默认 15 秒，可关（◷） |

在子代理会话里打开会**自动上溯到树根**并提示，所以不管你在哪一层，看到的都是同一棵树。

## 两个口径为什么要分开

以本机一个真实会话为例（9 个代理、283 步）：

```
billed 29,968,978
  未缓存输入   1,223,181
  缓存读      28,480,768   ← 95%
  输出           265,029
fresh = 1,223,181 + 265,029 = 1,488,210
```

`billed` 接近 3000 万，但真正新产生的只有 149 万。**只看 billed 会被吓到，看缓存占比才知道钱花在哪。** 所以两个口径都给你。

## 缓存命中率怎么算

```
缓存命中率 = 缓存读 /（缓存读 + 未缓存输入）
```

按上面那个会话：`28,480,768 / (28,480,768 + 1,223,181) = 95.9%`。

**分母里为什么没有输出和缓存写**：命中率问的是「这次请求的**提示词**有多少是从缓存里读到的」。
输出是模型新生成的，物理上不可能命中缓存；缓存写是往缓存里**存**，不是从里面**取**。把它们塞进分母
只会把命中率系统性压低，得到一个什么也不是的数。

**面板上三种显示**：

| 显示 | 含义 |
|---|---|
| `94.1%` | 正常 |
| `<0.1%` | 有请求，但几乎没命中缓存 |
| `—` | 一次请求都还没有，分母是 0 |

`—` 和 `0%` 是两件事，别混。前者是「没有数据」，后者是「有数据，但缓存一次都没命中」。

## 数据从哪来

直接读会话日志，**只读，不写任何东西**：

```
$DSH_HOME/sessions/<workspace>/<session>/session.v4.jsonl.zstd
```

按 header 里的 `parentSession` / `origin` / `delegationDepth` 还原代理树，把每个会话的 `assistant/message.usage` 累加，再沿树向上求和。

### 一个必须知道的坑

这个 `.zstd` 是**追加写、多帧**的。`zlib.zstdDecompressSync` 只解第一帧，于是会读到一条 202 字节的 `{"type":"session"}` 就结束 —— 看起来像「日志是空的」。

必须按 zstd 帧 magic（`28 B5 2F FD`）切帧，逐帧解压再拼起来。`selftest.mjs` 里专门有一条断言守着这个行为：

```
ok   单次 zstdDecompressSync 只拿到第一帧（这就是踩坑现象）
ok   decodeLog 拿到两帧
```

## 配置

`cordis.patch.yml` 里三项，都有默认值：

```yaml
- id: dsh-token-tree
  name: dsh-token-tree
  config:
    scanCacheMs: 4000    # 会话目录列表缓存
    maxSessions: 4000    # 最多扫描多少个会话目录
```

## 已知限制

- **父+子只在一个会话树内有意义。** 跨不同根会话的合计请用「上下文洞察」页面。
- **命中率是这一整棵树的合并值。** 它是「总缓存读 / 总提示词」，不是各个代理命中率的平均值——后者在代理之间用量差异大时会明显失真。
- **没有计时。** 本插件只汇总 token，不含墙钟时间；要时间看统计/轨迹页。
- **冷启动首扫较慢。** 1060 个会话 / 293 MB 全量解压约 7–12 秒（磁盘冷缓存时更久）；之后走缓存只要几十毫秒。正在写入的会话走**增量**路径，只解新增的 zstd 帧（实测 26.8x 加速）。
- **`reasoningTokens` 只有部分路由上报。** 实测本机 3001 条 usage 里 0 条带该字段，所以「推理」几乎永远显示为 0——这不是没推理，是路由没报。
- **`compaction/summary` 现在计入，但只在有压缩的会话里出现。** 面板会单独标注「其中压缩摘要 N 次」。
- **仅回环访问。** HTTP 路由只接受 127/8 与 ::1，且校验 Origin/Host 同源。

## 审计记录（第二轮，2026-11-13）

写了 4 个审计脚本对真实数据跑，发现并修复了 3 个真问题：

| 问题 | 严重度 | 证据 | 修复 |
|---|---|---|---|
| **漏算压缩 token**：只统计 `assistant/message`，但 `compaction/summary` 也带完整 usage | 中 | 6 个会话受影响，最高单会话漏 **1.76%**；本机合计漏 1,147,091 token | 加入 `compaction/summary` 分支，并单独记账 `compactionBilled/Fresh` |
| **每次刷新全量重解**：1060 个会话 × 293 MB，实测 **6991 ms**，而自动刷新是 5 秒一次 | 高 | `perf.mjs` 实测 | 改为 **mtime+size 命中缓存 + 只读增量帧**；实测 **26.8x**，且结果与全量逐字段一致 |
| **并发重复扫描**：两个面板或快速点击会同时各跑一遍全量 | 中 | 代码审查 | 加单飞（`inflight`），并发请求共享同一次扫描 |

同时做的加固：

- `findRoot` 在记录缺 `id` 时返回 `undefined` → 改为回退到 `parent` / 入参，并加环路防护
- 自动刷新间隔 5s → **15s**（扫描成本决定）
- UI 增加「其中压缩摘要 N 次，消耗 billed X（Y%）」提示
